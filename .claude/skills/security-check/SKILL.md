# セキュリティチェック

このアプリ（個人用・シングルユーザーの Streamlit + Gemini ライティングツール）を点検し、**まず日本語のレポートで報告**する。コードや設定の修正は、ユーザーがレポートを読んで「修正して」と言ってから行う。セキュリティの修正は挙動や使い勝手を変えることがあり（例：LAN 内のスマホから使えなくなる）、どこまで直すかはユーザーが決めることだから。

## 進め方

### 1. 前提を把握する

`CLAUDE.md` を読み、構成（`app.py` / `core/` / `tools/`）と、現在の利用形態を確認する。重要度は「どこで・誰が使うか」で大きく変わるので、ここを最初に押さえる。

- 手がかりがなければ「自分の PC で自分だけが使うローカルツール」を前提にする（CLAUDE.md にそう書かれている）。
- ユーザーが「公開したい」「デプロイしたい」「家族や同僚にも使わせたい」と言っていれば、その前提で評価する。認証がない、`.env` のキーを他人が使える、といった点の重要度が一気に上がる。

### 2. 自動スキャンを実行する

決まった観点を機械的に洗い出すスクリプトを同梱している。プロジェクトのルートで実行する：

```
.venv\Scripts\python .claude/skills/security-check/scripts/scan.py .
```

（venv がなければ Python 3.11 以上ならどれでもよい。標準ライブラリしか使っていない。）

スキャンでわかること：秘密情報らしき文字列（値はマスクして表示）、`.gitignore` と git 管理の状態、`.streamlit/config.toml` の危険な設定・未設定の項目、危険なコードパターン（`unsafe_allow_html`、`eval`、`subprocess`、キーのログ出力など）、依存パッケージのバージョン指定。

スキャン結果は**ヒントであって結論ではない**。誤検知もあるし、文脈を見ないとわからない問題（プロンプトインジェクションの影響範囲など）は拾えない。各ヒットは該当コードを実際に読んで、本当に問題か判断してから報告に入れる。

### 3. 手作業でレビューする

`references/checklist.md` を読み、観点ごとにコードを確認する。新しいツールが `tools/` に追加されていることがあるので、ファイル一覧は毎回取り直し、全ツールを見る。特に次の流れを追う：

- **入力 → プロンプト**：アップロードファイル・貼り付けテキストなど、外部の文章がどこからプロンプトに入るか
- **API キー**：`.env` / サイドバー入力 → `Settings` → `core/gemini.py` → エラー表示、の経路で表示・記録されないか
- **出力 → 表示**：生成結果が `st.markdown` などでどう描画されるか

### 4. 依存パッケージの脆弱性（任意）

`pip-audit` が venv に入っていれば `.venv\Scripts\python -m pip_audit -r requirements.txt` を実行する。入っていなければ勝手にインストールせず、レポートの「次のステップ」で提案するだけにする（環境を変えることになるため）。

### 5. レポートを書く

下のテンプレートどおりに、日本語でチャットに出力する。ユーザーがファイル保存を頼んだ場合や、保存先を指定された場合はそこに Markdown で書く。

## 重要度の付け方

重要度は「このアプリの実際の使われ方で、何が起きうるか」で決める。一般論で盛らないこと。ローカル専用ツールに「認証がない：高」と書くと、本当に直すべき指摘が埋もれ、ユーザーはレポートを信用しなくなる。

| 重要度 | 目安 |
|---|---|
| **高** | 現在の使い方のままで、秘密情報の漏えい・他人による API キーの不正利用・任意コード実行が現実的に起こりうる |
| **中** | 条件がそろえば被害が出る（同じ Wi-Fi に他人がいる、悪意ある文書を要約する、公開した場合など）、または被害は限定的だが簡単に防げる |
| **低** | 影響が小さい、または起こりにくい。直しておくとよい程度 |
| **情報** | 脆弱性ではないが知っておくべきこと（Gemini 無料枠でのデータの扱いなど） |

問題がないことを確認した項目も短く書く。「何を見たか」がわかると、ユーザーはチェックの網羅性を判断できる。

## 秘密情報の扱い

レポートにも途中の出力にも、API キーやパスワードの**値をそのまま書かない**。示すときは `AIza…(39文字)` のように先頭数文字と長さだけにする。チャットのログやレポートファイルは後で共有されることがあり、そこから漏れたら本末転倒だから。`.env` を `cat` で丸ごと表示するのも避け、キー名の有無だけ確かめる（スキャンスクリプトはマスク済みで表示する）。

## レポートのテンプレート

```markdown
# セキュリティチェック結果（YYYY-MM-DD）

**前提**：<例：自分の PC 上で自分だけが使うローカルツールとして評価>

## サマリー
高 N 件／中 N 件／低 N 件／情報 N 件
<全体の所見を1〜2文。一番先に対応すべきものを名指しする>

## 指摘事項

### 1. [高] <短いタイトル>
- **場所**：`path/to/file.py:行番号`（設定なら `.streamlit/config.toml` など）
- **内容**：何が問題か
- **起こりうること**：具体的なシナリオ（誰が・何をすると・どうなるか）
- **対策**：具体的な修正内容（設定値やコード片）。トレードオフがあれば書く

### 2. [中] ...

## 問題がないことを確認した項目
- <観点>：<確認した内容を一行で>

## 次のステップ
修正したい項目の番号を教えてください（例：「1 と 3 を修正して」）。<pip-audit 未導入なら導入の提案もここに>
```

指摘事項は重要度の高い順に並べる。

## 修正を頼まれたら

- 指定された項目だけを直す。ついでの修正はしない。
- CLAUDE.md の規約（`width="stretch"`、日本語 UI、ウィジェットキーのプレフィックスなど）を守る。
- 直したら、CLAUDE.md にある `AppTest` の方法で関係するページが起動することを確かめ、可能ならスキャンを再実行して指摘が消えたことを確認する。
- 何を変えたか、挙動がどう変わるか（例：「スマホから `http://<PCのIP>:8501` では開けなくなります」）を報告する。
